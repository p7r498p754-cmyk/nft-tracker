# NFT Tracker v0.5.5 — @nfttrecker_bot

**Включение v0.5.5.** В Settings → Secrets and variables → Actions задайте в Secrets TELEGRAM_BOT_TOKEN, PORTALS_API_KEY и OWNER_CHAT_ID. Сначала вручную запустите diagnose, затем отправьте /start боту и запустите monitor вручную. Проверьте /status после следующего цикла. Для работы по расписанию установите в Variables MONITOR_ENABLED=1. При пустой переменной доступны ручные запуски. Используйте публичный репозиторий и стандартный Linux runner. Выберите бесплатный тариф Portals (1 запрос/с).

В опубликованных ссылках встречается шаблон `https://t.me/portals/market?startapp=gift_{id}`. Проверьте его через «Поделиться» у активного лота и сравните коллекцию, номер и цену после открытия в Telegram. Затем внесите шаблон в PORTALS_LISTING_URL_TEMPLATE. Чтобы начать получать подтверждённые сигналы ещё до проверки ссылки, задайте ALLOW_NO_LINK_ALERTS=1.

Telegram-бот, который читает объявления Portals (официальный Partners API, только GET-запросы) и присылает
уведомление, когда цена минимум на 30% ниже оценки по недавним завершённым продажам. Бюджет: 0 ₽.
Ничего не покупает, не хранит ключи/пароли пользователей, платежей нет.

## Что изменилось по сравнению с v0.4

| Было | Стало |

## Как работает оценка

Оценка рыночной цены = **медиана** завершённых продаж Portals в одной валюте:

1. **exact** — та же коллекция + модель + фон + символ: ≥3 продажи за 14 дней.
2. **model** — та же коллекция + модель: ≥5 продаж за 14 дней; порог скидки выше на `MODEL_EXTRA_MARGIN` (10 п.п.), т.к. фон/символ могут объяснять низкую цену.

Перед расчётом отбрасываются выбросы (медиана ± 3·MAD). Нет сигнала, если данных мало, разброс квартилей >60% медианы, самая свежая продажа старше 72 ч, у подарка не указаны атрибуты, либо продажа — это тот же самый подарок.
Скидка = (оценка − цена) / оценка × 100%; показывается округлённой **вниз**, сравнение с порогом идёт по точному значению (Decimal, без float).

Перед отправкой лот перепроверяется (`/nfts/search`: статус `listed` и точная цена), старые события (>45 мин) пропускаются, один и тот же лот по той же цене не присылается повторно.
Это эвристика, а не гарантия: оценка ≠ цена перепродажи, прибыль не гарантирована.

## Статус проверки (на 23.11.2026)

**Проверено автотестами локально (123 теста, без вызовов API):** расчёт скидки и граница 30%, уровни оценки, выбросы/шум/устаревшие данные, разбор ответов, троттлинг 1 запрос/сек, повтор при 429, обработка 403/Cloudflare без обхода, проверка ссылок (https, белый список доменов, не главная), шаблон ссылки, защита от дублей, пропуск устаревших и проданных лотов, устойчивость к перезапуску (база на диске), блокировка бота пользователем, сбои Portals/Telegram, команды и кнопки, удаление данных, отсутствие секретов в логах, запуск CLI без сети.

**Не проверено (секреты Portals и Telegram отсутствуют; live-запросов не делалось):**
- реальные ответы Portals API и Telegram, реальная отправка сообщений;
- фактическую доступность API с предоставленным пользователем ключом — без первого запуска проверить нельзя;
- формат прямой ссылки на конкретный лот — **нигде не подтверждён**;
- не окажется ли IP GitHub заблокирован Cloudflare у Portals (в стороннем проекте сообщалось о блокировке серверных клиентов, ошибка 1010). Обход не используется: если это случится, бот честно напишет об этом, нужно разрешение от Portals;
- реальные значения цены и названий атрибутов в ответе от аккаунта пользователя, пока доступ к сети в среде тестов недоступен.

**Проверено по официальной документации Portals (не путать с live-тестом):** `/market/actions/` поддерживает `action_types`, `limit`, `offset`, `sort_by`, тип `purchase`; `actions[].amount` — строковая цена в GRAM. `/nfts/search` поддерживает массив `ids`, фильтр `status=listed` и возвращает `results[].price` и `results[].status`. См. https://docs.portals.tg/ru/developers/api/get-market-actions и https://docs.portals.tg/ru/developers/api/get-nfts-search .

**Не реализовано сознательно:** Telegram Market (по описанию v0.4, метод выдачи перепродаж доступен только пользовательским MTProto-сессиям; чужие сессии/парсинг запрещены, мной это заново не перепроверялось), Fragment (документированного API для объявлений не найдено), платежи и подписки Stars (только поле `tier` в базе как задел).

## Прямая ссылка на лот

Бот не придумывает адреса. Источники ссылки по порядку: поля `listing_url` в ответе API → шаблон `PORTALS_LISTING_URL_TEMPLATE` (переменная репозитория, содержит `{id}`, https, домены t.me / portal-market.com / portals.tg). Пока ни того ни другого нет, сигналы **не отправляются**, бот один раз в 12 ч пишет об этом, а `/status` показывает «ссылка не настроена».

Как получить формат: запустите workflow **diagnose** — он выведет имена полей ответа (без значений) и покажет, есть ли в ответе поле со ссылкой. Если поля нет, формат ссылки на лот даёт поддержка Portals; проверьте шаблон вручную на одном лоте и только потом сохраните его в переменной. Если хотите получать сигналы до этого, поставьте `ALLOW_NO_LINK_ALERTS=1`: придёт сообщение без кнопки и с пометкой «найдите лот по названию и номеру».

## Бесплатный хостинг: GitHub Actions

Проверено по документации GitHub: стандартные раннеры в публичных репозиториях бесплатны; в приватном — 2000 мин/мес (при запуске каждые 10 мин не хватит). Расписание `schedule` — best-effort: минимальный интервал 5 минут, запуски бывают задержаны на десятки минут; в публичном репозитории расписание отключается после 60 дней без активности в репозитории (тогда включите workflow на вкладке Actions заново).

Поэтому честно: **это не мгновенные уведомления**, а проверка примерно раз в 10 минут (фактически 10–30). Команды боту тоже обрабатываются при очередном запуске. Состояние (дедупликация, история продаж, настройки и позиция дозагрузки) хранится в кэше Actions: без личных идентификаторов, но кэш может быть удалён GitHub (7 дней без обращения) — тогда возможны единичные повторы сигналов и история продаж наберётся заново.

Обход механизмов засыпания не используется. Альтернатива для постоянной работы — запуск `python -m nft_tracker loop` на любом своём всегда включённом устройстве.

## Секреты и настройки

Секреты (Settings → Secrets and variables → Actions → **Secrets**): `TELEGRAM_BOT_TOKEN`, `PORTALS_API_KEY`, `OWNER_CHAT_ID`.
Переменные (**Variables**, необязательно): `PORTALS_LISTING_URL_TEMPLATE`, `PORTALS_PURCHASE_ACTION`, `PRICE_UNIT`, `TIMEZONE`, `ALLOW_NO_LINK_ALERTS`, `LISTING_PAGES` (1–36; по умолчанию 12).
Репозиторий публичный, поэтому в коде и логах нет ни ключей, ни chat_id; логи фильтруют токен и ключ. Не отправляйте их в чат; если ключ где-то засветился — перевыпустите (BotFather → /revoke; Portals → Partner API → новый ключ).

## Архитектура

```
nft_tracker/config.py     настройки из переменных окружения
nft_tracker/portals.py    клиент Portals (GET, 1 req/s, повторы, без обхода блокировок)
nft_tracker/valuation.py  оценка и скидка (Decimal)
nft_tracker/monitor.py    цикл: история продаж → свежие лоты → перепроверка → уведомление
nft_tracker/storage.py    SQLite: users (+tier), deliveries, sales, state
nft_tracker/bot.py        команды и кнопки      nft_tracker/telegram.py  API и тексты
nft_tracker/diagnose.py   безопасная диагностика
```
Мониторинг, пользователи/тарифы и настройки разделены: для публичной версии добавляются пользователи с `chat_id` и тарифы без переписывания оценки; платежи сейчас не реализованы и не активны. Для многопользовательского режима понадобится постоянное хранилище (не кэш Actions) и политика персональных данных.

Запуск тестов: `python -m unittest discover -s tests -t . -v` (Python 3.11+, зависимостей нет).

## Исправления v0.5.1 (ChatGPT)

- Проверка актуальности лота кешируется по паре **ID + цена**, а не только по ID: несколько изменений цены одного подарка за один цикл не создают ложный результат проверки.
- Свежесть рыночной оценки определяется только по продажам, оставшимся после удаления ценовых выбросов: единичная аномальная недавняя продажа больше не делает устаревшие сопоставимые данные «свежими».
- `/status` точнее описывает ссылки: даже без шаблона они могут поступить из официального API; формат прямой ссылки по-прежнему не подтверждён реальным вызовом.
- Добавлены регрессионные тесты; никакие реальные API в этой версии не проверялись.


## Исправления v0.5.2 (ChatGPT)

- **Оптимизация API:** когда найдено несколько подходящих объявлений, текущие цены и статусы проверяются **пачками до 20 NFT одним запросом** `/nfts/search`. Это сокращает число запросов к бесплатному Portals API. Если ответ не соответствует ожидаемой схеме, уведомления по такой пачке блокируются, ошибка фиксируется.
- **Более широкий охват рынка:** раньше монитор просматривал максимум 80 новых событий за цикл. Теперь по умолчанию просматривает до **240 событий** (12 страниц × 20), конфигурация `LISTING_PAGES` позволяет увеличить до **720** событий (36 страниц; допустимый offset до 700).
- **Оповещение о неполном охвате:** если поток оказался длиннее выбранного лимита страниц, предупреждение появляется в `/status` и логах. Это не гарантия полного охвата всех объявлений.
- **Дедупликация:** перекрывающиеся страницы и записи с ценой `60`, `60.0` и `60.000` не вызывают повторных уведомлений.
- **Первоначальная настройка:** при `OWNER_CHAT_ID=0` команда `/id` работает даже без ключа Portals. Для запуска `diagnose` ключ обязателен.
- **Проверка проекта:** 100 офлайн-тестов проходили в v0.5.2 (Python 3.11–3.13 рассчитаны, отдельно CI ещё не запускался). Реальный API и прямые ссылки остаются непроверенными.

**Важно:** Portals по документации отдаёт последние рыночные действия, но не гарантирует, что конкретный лот останется доступен после отправки сигнала. По умолчанию без подтверждённой ссылки сигнал не отправляется. Нельзя воспринимать рыночную оценку или скидку как гарантированный результат сделки.


## Изменения v0.5.3 (115 локальных тестов)

- Ошибки отправки Telegram-команд больше не подтверждают update преждевременно. При временной ошибке команда будет повторена в следующем запуске. При сетевом сбое после успешной отправки возможен повторный ответ — это безопаснее, чем потеря команды.
- `python -m nft_tracker run` теперь возвращает код 1 при ошибке Portals или обработки команд, чтобы неудачный GitHub Actions запуск был виден как ошибка. Шаг `Save state` выполняется с `if: always()` даже при такой ошибке.
- При переполненной ленте Portals время последнего события не продвигается: это оставляет возможность добрать пропущенные объявления при расширении глубины проверки. События из будущего не меняют курсор. Курсор также сохраняется неизменным, если кандидат не удалось проверить или доставить, чтобы дать возможность повторить проверку.
- Часовой пояс по умолчанию — `UTC`; при необходимости можно задать `TIMEZONE` как IANA-идентификатор.
- Ошибки 400 и 403 при ответе пользователю считаются постоянными: обновление пропускается, чтобы один недоступный чат не блокировал остальные команды. SQLite-соединения закрываются при завершении работы, включая аварийные пути.

Локальные тесты работают на фиктивных данных; настоящая сеть, корректность выдачи API и ссылки на конкретные лоты по-прежнему требуют проверки. Состояние в GitHub Actions Cache сохраняется с риском удаления или доступа со стороны участников публичного репозитория: не добавляйте в него токены, ключи или чужие персональные данные.


## Изменения v0.5.4 (123 локальных теста)

- **История продаж загружается постепенно, а не только один раз.** На каждом цикле опрашиваются до 3 страниц новых продаж, а пока идёт начальная подготовка — дополнительно до 5 страниц более старой истории. Прогресс сохраняется в SQLite, при следующем запуске загрузка продолжается с перекрытием одной страницы для снижения риска пропусков. В этом режиме дополнительных запросов к бесплатному API больше, но действует ограничение скорости 1 запрос в секунду.
- **Ограничение официального API учитывается явно:** offset рыночной ленты не может превышать 700, поэтому полную историю всех коллекций за 14 дней получить гарантированно нельзя. Если достигнут предел, `/status` сообщает о неполной истории и оценка использует только реально подтверждённые продажи. Пагинация по смещению не является неизменяемым снимком рынка; при очень интенсивном потоке некоторые старые события могут быть пропущены.
- **Безопасность при изменениях схемы API:** некорректные события `listing`, `price_update` или `purchase` больше не игнорируются молча — цикл сообщает об ошибке и не продвигает курсор объявлений. Данные HTML в номере подарка и подписи валюты экранируются, чтобы случайные символы не ломали уведомления.
- **Честная проверка:** новые сценарии проверены на искусственных HTTP-ответах и SQLite с реальным закрытием/повторным открытием файла. Обращений к живым API не выполнялось.

Это по-прежнему **демонстрационная инфраструктура мониторинга**, а не подтверждённый продукционный сервис. Для отправки реальных уведомлений нужны действующие ключи в GitHub Secrets, диагностический запуск с доступом к API и подтверждённые прямые ссылки на активные лоты.
